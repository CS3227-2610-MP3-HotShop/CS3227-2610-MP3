# Project Reflections

## Jonathen Cheng — buyer AI Search and development workflow

My work focused on buyer AI Search, the PostgreSQL and private image-storage integration, and comparing single-agent and multi-agent development. I used AI assistance to produce specifications, code, tests and reviews. My responsibility was to make the requirements and workflow decisions, question the results, and decide what evidence was sufficient to accept the work.

For AI Search, I treated both the buyer's request and the model's response as untrusted. A request such as "books below $20" should produce a proposal for the existing search filters. It should not give the model permission to generate SQL, access accounts or change marketplace records. The application accepts only supported fields, enum values and bounded prices, rejects unexpected fields, and converts the proposal into the existing search model. The buyer reviews the proposal before choosing **Apply filters**.

This changed how I thought about prompt injection. Asking the model to ignore malicious instructions can help, but the stronger protection is limiting what a response can cause the application to do. I found it more useful to ask what each security test actually demonstrates than to rely on a large passing-test count. The validator and connection tests provide evidence at several boundaries, from the fields a proposal can contain to how the client handles a stalled response.

To check that proposals stay within their permitted authority, tests submit fields such as `sql`, `sellerId`, `userId` and `isAdmin` and assert that validation rejects them. Even an unknown field containing `null` must be rejected. This gives evidence that a model response cannot extend the supported search contract by introducing a privileged field; the application does not simply ignore the field and continue with an apparently valid proposal.

The validator tests also check types and boundaries. They reject negative or excessive prices, reversed price ranges, floating-point or string prices, unsupported categories and conditions, and titles beyond the Unicode character limit. Valid boundary values are also tested. These cases help detect accidental acceptance through rounding, type conversion or off-by-one mistakes, while checking that legitimate input still works.

At the connection boundary, the client tests supply malformed JSON, duplicate keys, invalid text encoding, truncated completions, and responses containing function or tool calls. They assert an invalid-response result rather than a usable search proposal. This gives evidence that the application fails safely for those response forms instead of accepting partial data or treating a tool request as an instruction to execute.

Credential protection is checked using a local HTTPS server that returns a redirect to a second server. The test checks that the second server receives no request and that the client does not retry. Other tests return provider errors and assert that the returned failure contains neither the fake API token nor the raw provider body. These are observable checks of redirect handling and returned errors, rather than assumptions that HTTPS alone prevents credential leakage.

Resource and lifecycle tests exercise request-size rejection before dispatch, the response-size boundary at 65,536 and 65,537 bytes, a response that stalls after starting, and closing a client with a pending request. They check safe failure or cancellation outcomes. This provides evidence that these specific oversized and stalled cases do not become successful proposals or leave the caller waiting indefinitely.

The assurance comes from connecting an adverse input to an observable application decision: reject the proposal, send no redirected request, return a fixed failure, or complete a stalled operation. A test that merely checked that the model returned some text would not establish these properties. I also need to respect the scope of an assertion. For example, the validator test that preserves SQL-like title text as a literal does not execute a database query; by itself, it is not an end-to-end SQL injection test.

There are important limits. A model could return a structurally valid proposal with the wrong category or price and still pass validation. These tests do not prove that it understood the buyer, resisted every prompt injection, or behaved safely inside the provider's own systems. The preview and explicit apply step preserve the buyer's choice, but they do not guarantee that the buyer will notice a misleading suggestion. The first benchmark's 42 security-tagged cases were a subset of its 76 tests, not 42 independent guarantees. The examples above also include later connection tests; they should not be retroactively counted as evidence from the original frozen benchmark.

Resource use was another boundary. I chose a separate **AI Search** button because ordinary searches should not automatically consume LLM requests. The application also uses bounded messages, deadlines, safe failure categories and no automatic retries. The integrated production transport shares a 90-request rolling-minute ceiling across buyer and seller AI calls, while preserving the seller's per-account limits. That ceiling is process-local; it does not enforce the provider's monetary budget or coordinate separate deployments. I learned to distinguish an application safeguard from a guarantee about the external provider.

The connection experiments used local HTTPS fixtures rather than live SoC requests. This made failures repeatable and avoided spending the provider budget, but it could not establish live interoperability. Later connection work had to follow the actual SoC request format. I should describe these as different kinds of evidence rather than call mocked tests proof that the hosted AI feature works.

Writing a product specification, technical design and task plan helped me separate what the buyer should experience from how the application should implement it. For example, the UI requirement became an explicit **AI Search** action, a preview and a separate apply step, while normal search remained available. This gave implementation and review agents a shared contract instead of letting each agent invent its own interpretation.

However, a shared test suite can consistently measure the wrong behavior. In the UI benchmark, both workflows passed 18 of 21 fixed tests. The three failures came from a helper that requested an AI preview with an empty query, although the requirement said to reject empty input. Both implementations rejected it. I learned that I cannot simply blame the implementation or weaken an assertion to obtain green tests: I need to trace the disputed test back to the approved requirement. We retained the original benchmark outcomes and recorded the conflict rather than retroactively claiming complete acceptance.

The final Storage work provided a different lesson. Passing offline checks and reviews did not reveal that the browser image chooser failed on its first click. Real Chrome checks exposed the problem: the handler was attached too late, the page became disabled while waiting, and JPro required click selection to be enabled explicitly. The correction bound the picker before use, kept cancellation interactive and prevented abandoned selections from starting application work. We then checked actual uploads, image retrieval after replacing the app container, and removal of the test objects. I learned that a specification needs acceptance checks at the platform boundary, not only tests around a convenient internal interface.

My initial expectation was that multiple agents would consume more resources but finish faster and produce better work through specialized roles. I tested three bounded tasks from equivalent starting checkpoints and shared requirements:

For the search contract and validator, both workflows passed all 76 tests. The multi-agent run took 320 seconds overall, compared with 329 seconds for single-agent. For the SoC connection and buyer adapter, both passed all 149 tests, but multi-agent took 398 seconds compared with 271 seconds for single-agent. For the explicit AI Search UI, both passed 18 of the 21 fixed tests, with the shared test problem described above accounting for the three failures. The recorded elapsed-time ranges were 493–512 seconds for multi-agent and 472–497 seconds for single-agent.

The validator produced its first multi-agent candidate at 223 seconds versus 329 seconds for single-agent, but the 97-second review interval reduced the end-to-end difference to nine seconds. The larger connection task favored the single-agent run on observed time, and the UI timing ranges overlapped. These results did not support my expected general speed advantage for the multi-agent workflow.

There were nevertheless useful quality differences. In the connection task, independent reviewers caught body-cancellation and network-error classification defects in the multi-agent candidate despite its passing tests. They stopped acceptance rather than treating green tests as sufficient. Common source assessment later identified four attributable findings in that candidate and one in the single-agent candidate. The findings differed in severity, and one possible race was inferred from source rather than reproduced. More agents therefore did not automatically produce fewer defects; detecting a defect and preventing it are separate outcomes.

The multi-agent UI implementer also added four configuration and unavailable-service regression tests. The single-agent candidate implemented those paths but provided source-only evidence. I consider the additional executable protection a concrete advantage of that run. It suggests that a focused role and checklist can encourage more thorough verification, but the tests came from the implementer, so I cannot attribute them specifically to independent review or prove that role specialization caused the difference.

An important limitation is that I designed and adapted these specifications and coordination rules myself while learning. This was not a comparison against a mature, optimized multi-agent workflow. Both arms used the same Luna implementer model, and the multi-agent workflow largely used one implementer followed by final reviewers. It offered little implementation parallelism. The tasks may also have been too small to benefit from several specialists working on independent areas. Each task had only one paired run; execution order, caches and coordinator delays were not fully controlled. These results concern my workflow configuration, not multi-agent software engineering in general.

Resource measurements were also limited. For the SoC task, my recorded session-allowance display dropped by eight percentage points for multi-agent and three for single-agent. These were coarse manual readings; I revised the multi-agent endpoint to include more wrap-up, and exact tokens or credits were unavailable. The UI runs used different allowance windows, one reached zero, and the single-agent run encountered a restricted-shell delay. I can report those observations, but not turn them into precise cost ratios or attribute all elapsed time to agent reasoning.

The practical change I made was to reduce unnecessary handoffs: one implementer owns a complete approved batch, with independent specification and security review of a stable candidate at the end. I also limited context reads, shortened reporting and planned one grouped correction pass, allowing further passes only for confirmed errors. For small tasks I would start with one implementer and add independent review where the consequences justify it. For a stronger future experiment, I would use repeated, more complex tasks with genuinely independent implementation areas and clearer timing boundaries. My main lesson is to judge the workflow by the defects it detects, the regression evidence it leaves and the human decisions it supports, alongside time and resource use.
