# Reflection on AI-Assisted Software Engineering in HotShop

This implementation of this set of new features exposed me to different workflows like SDD and Multi-agent workflows. Which also branched into understanding concepts like context engineering in order to properly optimise the efficiency of the agents working. A balance needed to be achieved between token usage as well as LLM context and capabilities. Creating a user-facing LLM feature also allowed me to consider different prompt injection scenarios, and subsequently creating a set of test cases to verify the security of my feature.

## AI security

For the AI description feature, I mainly considered attacks through the product title and the response returned by the AI service. A seller could enter a title that tells the AI to ignore its instructions, reveal private information or run commands. Some attacks pretend to be system instructions, while others hide instructions using encoding, similar-looking letters, invisible characters or another language. The test cases cover these examples. They also include normal titles such as “System design textbook”. This helped me understand why simply blocking words like “system” would stop valid input without solving the problem.

I learned that telling the AI to behave safely is not enough. The application also needs to limit what the AI can access and do. HotShop sends only the title, condition and fixed instructions as product context. The API key is sent separately in the request header, and private account details, database records and source files are not included. The connection uses HTTPS and does not follow redirects. The AI has no application tools for accessing files, running commands or changing the database. Responses containing structured tool calls are rejected, and returned text is never run as code.

There are also limits to prevent excessive requests or long waits. Each account can have only one request running at a time, with up to five attempts in a rolling minute and thirty in a rolling hour. Requests are not retried automatically. The connection timeout is 10 seconds, and the transport has a 45-second deadline. Request and response sizes are limited, and generated descriptions cannot exceed 100 words. The application checks the login session and whether the form has changed before inserting a result, so a late response does not overwrite newer edits. Overall the limits help to keep the response provided by the LLM service reasonable in length, as well as preventing excessive use of generation credits when there is little merit to longer messages.

The tests check these protections using fake private values and a local test server. They inspect what is sent to the AI service, check that errors do not expose secrets, and compare files and database contents before and after generation. Other tests cover invalid responses, tool calls, request limits and changes to the form or session. These tests are useful, but they cannot fully judge whether a generated description follows an attacker's instructions.

That is why I had the agent prepare a page that documented the test prompts as well as the returned text from the LLM. The first recorded live test run passed the automated checks, but I found a small semantic problem with the `attack-internals` case, where the response from the LLM seemed to take the malicious request a little too much into consideration when generating the description. After an approved change to the prompt, the second run passed both automated checks as well as my manual review. I learned that a passing test result does not always mean the AI's answer is suitable and the user still needs to read the output and check its meaning.

The seller also stays in control of the final listing. Generation happens only when requested, and the result remains editable and unsaved until the seller chooses to save it. The text returned by the AI does not trigger the save action, giving the user an opportunity to review what was returned by the LLM.

## Spec-driven development

I learned that I need to explain more than the main idea of a feature before asking an agent to build it. For HotShop, saying “generate a description” would leave several questions unanswered. I learned from my workflow in MP2 that having the LLM clarify development decisions with you before writing documentation or implementation allows you not only the opportunity to use the LLM to consider certain edge cases that you might not have considered, as well as giving you more appropriate control of the design of the feature instead of leaving decisions to the agent.

I also learned the importance of making the specification files not only understandable by the coding agent, but also legible by human readers, so that I could verify each step of the specification planning process before approving and telling the agent to generate the next set of documents. An example of this would be requiring each task in the specification plan to have a concrete set of steps, both for me to understand the task, as well as for the coding agent to follow. Having the agent use the plan file as a checklist also allowed me to verify which tasks had been completed and which are still pending.

I also learned that changing a requirement means updating more than the code. I need to update the product specification, technical design and plan, then make sure the implementation, tests and guides follow the same decision. One example was changing how the application loads its AI service settings. If only some required environment settings are present, generation should be disabled instead of filling the gaps from a local file. Recording this rule clearly gives me something to check against the tests.

Developing software using SDD also meant that there was going to be additional costs incurred from the writing of the specification files. This put more emphasis on exercising proper Context Engineering practices, like shortening skill descriptions and agent artifacts like AGENTS.md in order to not have valuable tokens wasted on extra generation work. I created shorter copies of my partner's SDD skills in an attempt to both speed up the agent as well as cut down on token costs, while also catching errant behaviours where my partner's logging instructions had been added on top of mine to AGENTS.md, meaning that the agent was creating two separate interaction log files for each task.


## Multi-agent software engineering

In the context of Spec-Driven Development, the use of a Multi-agent workflow in Software Engineering makes a lot of sense. This is because SDD by itself requires a plan to be created with the relevant tasks separated from one another. This means that different subagents can be spawned for each individual task, without the added step by an orchestrator to reason with and delegate work to the respective agents as that has already been done as part of SDD.

Of course this neccesitates that the tasks are split properly beforehand, i.e. if testing and implementation are to be handled by separate agents, then a task should not consist of both testing and implementation. It is also important within the planning document that the sequence of tasks to be completed is clearly laid out in the form of dependencies. For example each task can define which other task in the document has to be marked as completed, before this task can be run. When there are tasks that are not part of a sequential chain of dependencies, that is when multi-agent workflows can be used to speed up the development process.

A useful handoff identifies the approved task and specification version, acceptance criteria, dependencies, permitted files, actual commands and results, as well as both unresolved blockers and a list of what has been explicitly approved by the human engineer. Without these, a later agent may review the wrong code or mistake an assumption for approval. Errors can slip through during specification interpretation, test design, implementation shortcuts or review summaries; malicious instructions can exploit the same transitions. Reviewers therefore need access to the actual artifacts rather than only another agent's conclusions.

The evidence should be concise and verifiable: changed files, requirement-to-test links, actual check outcomes and explicit limitations. For me this was located within the planning file itself, where each task documented what was done as well as specifically what was defined not to be claimed as completed once a task was marked as completed by the agent. Other agents reading from the planning file would thus be able to get a summary of what a previous agent had completed and have a more accurate understanding of where to start as well as the deliverables for their own task.
